What it is

  • The vocabulary plus the functions between its parts. A pose is a point and an orientation in a frame. A trajectory is poses (or joint angles) over time. A point cloud comes from a depth image plus camera info. The relationships ship with the types: pose.shifted(dz=-0.1, local=True), traj.joint_state_at(t), PointCloud.from_depth(depth, info).
  • ROS's domain model without ROS. Same packages and field names, so the ROS docs are our docs. The values are frozen, numpy-backed and full of helpers. ROS 2 wire format is an export, not the programming model.
  • The bottom of the stack. Runtime dependency: numpy only, proven below. like_keras/Clank, bam_traj_gen, traj_compare and the sim can all sit on it.

The Trajectory: one entity, many views

Storage is struct-of-arrays: one read-only array per field, with time on axis 0. Every other shape is a view (free, same memory) or a computed new value. Your instinct was right, and the July tuple-backed version couldn't deliver it: its to_numpy() view was a copy.

Solid = view (no copy, measured with np.shares_memory in the tests) · dashed = computes a new value. joint() copies its columns (numpy fancy indexing); its row slices are views.

How general should a type be? The function decides

Your framing is now rule 8 in docs/DESIGN.md. A function that works on anything with samples over time takes a Trajectory: resample, window, plot, concatenate. One that needs joint angles takes a JointTrajectory: joint(), limit_violations(), joint_state_at(). One that needs poses takes a PoseTrajectory: transformed(), shifted(), path_length(). The type is the validation. A new domain subclasses Trajectory and declares its sample() fields in its own file. It gets indexing, iteration, interpolation, plotting and serialisation for free, plus a generated point type (tested with a GripperTrajectory).

ROS 2 is an export, and it is real

robot_msgs.ros converts every type with a ROS counterpart to the actual ROS 2 Jazzy message classes (rosbags' typestore, no ROS install; vision_msgs 4.1.1 registered from upstream) and writes standard rosbag2 mcap bags that Foxglove opens. What ROS has no slot for is never dropped silently.

  • Independent oracles: rotation, compose, euler, slerp and interpolation are checked against scipy, a test-only dependency. ROS conversions round-trip through rosbags' own CDR serializer. A bag is written and read back with rosbags' Reader.
  • Contract tests over every type, via a catalog of one example each. Each must be a frozen dataclass, and must pickle, deep-copy, JSON-round-trip and npz-round-trip losslessly. Adding a type without a catalog example fails the suite.

What needs you

  1. Domain: robotmsgs.com is unregistered (registry RDAP; price and premium status unknown, since there's no Cloudflare registrar token). Buy it on Cloudflare yourself. Default if silent: nothing bought.
  2. Which consumer migrates first? I recommend traj_compare, whose Situation is already JointTrajectory + PoseTrajectory in disguise, then bam_arm's NumpyTrajectory. Default: nothing migrates until you say.
  3. Publish? A private GitHub repo, plus reserving robot-msgs on PyPI (free today). Default: local only.
  4. numpy over tuples reverses the July FR-TRAJ-JOINT-TRAJECTORY-VIEWS acceptance ("tuple-backed"). Default: numpy, as built.

Left, and deliberately not done

  • Next, not blocked: cubic/quintic interpolation like ros2_control's JTC (v1 is linear / slerp / hold); a frame-tree type (TFMessage + lookup("base_link", "tool0")); PoseArray, PoseWithCovariance, Odometry, LaserScan, CompressedImage, markers; distortion in CameraInfo.project; a Rerun / Clank-plugin view.
  • Not done on purpose: migrating bam_ws, traj_compare or like_keras (integration is your call); pushing or publishing; buying the domain; an audit (you didn't ask). The Trajectory core is the long-lived contract here, so it may be worth a /llm-judge.
